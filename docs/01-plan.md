# 01. План разработки

## 1. Цель и границы

Перенести демо в продуктовое веб-приложение для внутреннего использования: несколько операторов
одновременно ведут базу участников конкурса, видят картинку-билет с подставленными данными
выбранного участника, печатают/сохраняют/копируют её. Админ управляет людьми, проектами и настройками.

**Нагрузка:** внутренняя, десятки одновременных пользователей, проекты до ~5–20 тыс. участников.
Масштабирование «в ширину» не требуется → монолит, один экземпляр, ресурсы минимальны.

**Вне скоупа v1:** микросервисы, горизонтальное масштабирование, e-mail, OAuth/SSO, офлайн-режим,
мобильные нативные приложения, перенос данных из десктопной БД.

## 2. Что берём из референсов

### Из демо (`ref/web`) — переиспользуем
| Что | Где | Комментарий |
|---|---|---|
| Дизайн-токены, `ui.css`, компоненты Avatar/Menu/Modal/Toast | `frontend/src/styles`, `components` | Основа UI |
| `renderTicket` — один рендер на canvas для превью/копии/сохранения/печати | `frontend/src/lib/renderTicket.ts` | Сохраняем принцип WYSIWYG |
| Идея хаба (комнаты по проектам, presence) | `backend/internal/realtime` | Перепишем как `repository/memory` за интерфейсами `service` (см. ниже) |
| Раскладка печати A4, 7×4 см | `frontend/src/lib/print.ts` | Размер станет настройкой проекта |

### Из демо — **переписываем** (известные упрощения)
| Проблема в демо | Решение |
|---|---|
| Картинки/аватары в Postgres (`bytea`/data URL) | Картинки проектов — файлы на диске (content-hash), аватары — маленький `bytea` ≤ 256 px |
| Один долгоживущий JWT (7 дней) в localStorage + токен в query WebSocket | **JWT остаётся (HMAC)**, но: access 15 мин только в памяти SPA + ротируемый refresh-JWT в httpOnly-cookie, состояние в Redis (на iOS localStorage чистится ITP, украденный долгий JWT не отозвать); WS — токен первым кадром, не в URL (иначе попадает в логи) |
| Нет ролей, все видят всё | RBAC: `admin`/`worker`, права проверяются в сервисном слое |
| «Блокировка» строки — только индикатор | Серверные soft-lock с TTL + optimistic `version` → 409 при конфликте |
| Медленному WS-клиенту молча теряются сообщения | Переполнение буфера → закрыть соединение, клиент переподключается и делает resync |
| Один идемпотентный SQL без версий | goose-миграции, версионирование, откат |
| Экспорт только CSV, нет тестов, нет метрик | XLSX/CSV, тесты на всех слоях, логи+метрики |
| Фронт отдаётся отдельным nginx | Один Go-бинарник отдаёт API и встроенный SPA (`go:embed`) |

### Из десктопа (`ref/tip`) — функции, которые должны быть в вебе
Генерация билета по строке · БД любого размера · редактирование «как в Excel» · печать (7×4 см) ·
сохранение одной/нескольких картинок · копирование в буфер · настройка шрифта/цвета/позиции ·
добавление N одинаковых записей · экспорт в XLSX · очистка базы (в десктопе — под отдельным паролем,
в вебе — только админ + подтверждение) · масштабирование картинки (zoom) · поиск.
Темы (7 QSS) — **не переносим**: вместо них две темы — тёмная (по умолчанию, из макета) и светлая (проектируем по токенам).

> Десктоп под GPLv3: код не копируем, берём только поведение.

## 3. Окружение (подготовлено в этой сессии)

Установлено для Claude Code: плагины `gopls-lsp`, `typescript-lsp`, `frontend-design`, `context7`
(актуальные доки библиотек), `playwright` (e2e, включая WebKit), `security-guidance`.
Go-инструменты: `gopls`, `goose`, `golangci-lint` (в `~/go/bin`). Уже были: `code-review`, `simplify`, `ponytail`.

**Не хватает на машине разработчика:** Node.js LTS (нужен для фронтенда) — ставим в Фазе 0
(`winget install OpenJS.NodeJS.LTS`). Docker Desktop есть.

## 4. Фазы

**Код пишет Claude Code, заказчик согласует и проверяет.** Поэтому оценка дана в двух величинах: **часы активной работы** (написание кода, тестов, отладка) и **календарные рабочие дни** с учётом ваших согласований и действий,
которые невозможно ускорить (реальные iPhone/Mac, носитель узбекского, доступ к серверу). Точность — ±40 %; главная неопределённость — особенности iOS/Safari и ожидание людей.

### Фаза 0 — Фундамент · ≈ 3–4 ч работы · ~1 день
* Монорепо: `backend/`, `frontend/`, `deploy/`, `docs/`, `Taskfile.yml` (go-task, удобнее make на Windows).
* Go-модуль, **каркас Clean Architecture** (`domain` / `service` / `handler` / `repository` / `platform`, сборка зависимостей в `main`; см. `02-architecture.md`, раздел 3),
  `cmd/tipd` (подкоманды `serve`, `migrate`, `admin create`), конфиг из env, graceful shutdown.
* **Проверка слоёв в CI:** `depguard` + архитектурный тест на импорты — вводим сразу, пока нарушать нечего.
* Подключение БД (`database/sql` + pgx stdlib), goose + embed, `AUTO_MIGRATE`, интерфейс `Tx` в `service` и его реализация в `repository/postgres`.
* **zerolog + diode** (JSON, неблокирующий вывод, сэмплинг), request-id, `/healthz`, `/readyz`, `/metrics` на внутреннем порту.
* `docker-compose.dev.yml` (Postgres 18 + Redis), Vite-проект, прокси `/api`.
* **Дизайн-система фронтенда:** токены цвета, типографики и **движения** (длительности, easing), базовые анимированные компоненты (Button, Modal, Menu, Toast, Skeleton), замер размера анимационной библиотеки; **две темы** (тёмная по умолчанию + светлая) и каркас i18n (`ru`/`uz`).
* Линт/форматирование: `golangci-lint`, Biome; генерация (`oapi-codegen`, `openapi-typescript`) в `task gen`; CI (GitHub Actions): lint + test + build.
* Проектный `CLAUDE.md` с конвенциями; `.claude/settings.json` с allowlist команд.
* **Готово когда:** `task dev` поднимает БД+бэк+фронт, `task test` и CI зелёные.

### Фаза 1 — Контракт и данные · ≈ 5–7 ч · ~1 день
* **`backend/api/openapi.yaml` (OpenAPI 3.1, contract-first)** — единый источник правды; `oapi-codegen` → Go-DTO и `ServerInterface`, `openapi-typescript` → типы фронта; **Swagger UI на `/api/docs`** (embed, кнопка Authorize с JWT); `x-required-permissions` на операциях; линтер спеки и проверка дрейфа в CI.
* Миграции `00001…00005` (см. `03-database.md`).
* Доменные сущности и ошибки (`domain`), интерфейсы `Repository` в `service/*/ports.go`, их реализации в `repository/postgres` на чистом SQL.
* Тестовая обвязка: testcontainers-go (реальный Postgres), фабрики данных, in-memory фейки интерфейсов для тестов `service`.
* **Готово когда:** миграции up/down проходят в CI, репозитории покрыты интеграционными тестами.

### Фаза 2 — Аккаунты, JWT, динамические роли · ≈ 8–12 ч · ~2 дня
* Argon2id; **access и refresh — JWT HMAC-SHA256** (два секрета, 15 мин / 30 дней), refresh в httpOnly-cookie `tip_rt`. **Токенов в Postgres нет.**
* **Всё состояние токенов — в Redis:** интерфейс `TokenStore` в `service` + `repository/redis` (`rt:*` — allow-list refresh с атомарной Lua-ротацией и reuse detection, `revfam:*` — отзыв цепочки, `bl:jti:*` — выход, `bl:user:*` — отсечка при деактивации/смене роли/пароля), `REDIS_FAIL_MODE=open`, закрытие WS отозванного пользователя, тесты на testcontainers (Redis).
* `login/refresh/logout/me`, смена пароля, профиль (имя, цвет, аватар с ресайзом, «Внешний вид»: язык ru/uz и тема), рекомендация сменить временный пароль.
* Админ: CRUD пользователей, сброс пароля (временный показывается один раз), деактивация, защита «последнего админа».
* **Динамические роли (в БД, управляются админом):** миграция `00002_rbac` (`permissions`, `roles`, `role_permissions`, `user_roles`, `authz_state`), каталог прав в `domain/permission.go` + `SyncPermissions` при старте, системные роли `admin`/`worker`, `service` (CRUD, назначение, нормализация зависимостей прав, инварианты `LAST_ADMIN`/`ROLE_IN_USE`/`ROLE_SYSTEM`).
* **Права в access-JWT** (`roles`, `perms`, эпоха `pe`): `Actor.Can(perm)` в `service` без БД; `401 TOKEN_STALE` + прозрачный refresh при смене ролей; кадр `reauth` для WS; HTTP-middleware `RequirePerm` только для `/admin/*`; rate-limit входа (`Limiter`), аудит-лог.
* **Пароли:** argon2id + pepper (только хэш в БД), перехэширование при смене параметров; создание пользователя и сброс **генерируют новый случайный пароль** (показ один раз, `passwordTemporary`), при первом входе UI **рекомендует** сменить пароль (`FORCE_PASSWORD_CHANGE` — опциональное принуждение).
* Фронт: Login, Профиль, модалка «Смените пароль», `/admin/users`, **`/admin/roles` (матрица прав)**, guards маршрутов и элементов по `perms`.
* **Готово когда:** каждое право каталога покрыто тестом «без права → 403»; смена роли у пользователя даёт `TOKEN_STALE` → новый токен с новыми правами; создание/сброс выдаёт новый пароль, первый вход показывает рекомендацию.

### Фаза 3 — Проекты · ≈ 6–8 ч · ~1,5 дня
* CRUD, finish/reopen/delete (admin), список с поиском и разделением «Активные/Завершённые».
* Загрузка картинки: проверка magic bytes + декодирование, лимиты размера/пикселей, запись в хранилище по sha256, GC сирот.
* Настройки плейсхолдеров (шрифт, размер, обводка, цвета, начертание, позиция) + перетаскивание на превью (Pointer Events).
* Фронт: Projects, ProjectSettings (по макету, экраны 2 и 5).
* **Готово когда:** админ создаёт проект, грузит картинку, настраивает плейсхолдеры; работник видит активные и завершённые (завершённые — read-only).

### Фаза 4 — Участники и рабочее место · ≈ 10–14 ч · ~2,5 дня
* API участников: список, массовое добавление, PATCH с `version`, bulk-delete, очистка, журнал печати, импорт/экспорт XLSX+CSV.
* Таблица: виртуализация (5 000+ строк), инлайн-правка, мультивыбор, клавиатура, поиск на клиенте.
* Билет: canvas, шрифты self-hosted, копирование (Safari-совместимое), сохранение (ZIP при >1), печать A4 (после диалога — запись в аудит).
* Фронт: Workspace (экран 3), панели с max/close, модалка «добавить N записей».
* **Интерактив и анимации рабочего места:** вставка/удаление строк, crossfade билета, отмена удаления (тост «Отменить»), вставка строк из Excel, обводка занятой строки цветом пользователя с подсказкой.
* **Готово когда:** один оператор проходит весь цикл «добавил → выбрал → напечатал» на Chrome и Safari.

### Фаза 5 — Realtime · ≈ 6–8 ч · ~1,5 дня
* Hub по модели «горутина на комнату», presence, курсоры (focus), soft-lock строки с TTL, heartbeat.
* События `rows.upsert/delete`, `project.updated`; reconnect с backoff, resync по `version`; поведение при уходе вкладки в фон (iOS).
* Конфликты: 409 `ROW_LOCKED` / `VERSION_CONFLICT` + UX: строка блокируется, обводится цветом редактирующего, при наведении подсказка «Редактирует Азам».
* Нагрузочный тест: 100 WS-клиентов × 10 проектов, замер памяти/CPU.
* **Готово когда:** два браузера видят друг друга, не могут одновременно править строку, состояние восстанавливается после обрыва сети.

### Фаза 6 — Наблюдаемость и эксплуатация · ≈ 6–8 ч · ~1,5 дня
(логирование/метрики закладываются с Фазы 0, здесь — доводка и инфраструктура)
* Метрики HTTP/WS/DB/бизнес, коллектор диска, pprof на внутреннем порту.
* Compose-стек: Prometheus, **Loki + Vector**, Grafana (дашборды как код), node_exporter, `mem_limit` на каждый контейнер, zram; ретенция из `OBS_RETENTION_DAYS`; лимиты по памяти/диску.
* Бэкапы `pg_dump` + архив `uploads/` с ротацией; проверка восстановления; ранбук.
* Клиентские ошибки → `POST /client-errors` → логи.
* **Выгрузка бэкапов вне сервера** (`rclone` + `crypt`, провайдер по конфигу, метрика и плашка «последняя выгрузка»); **алерты без Telegram:** Grafana alerting → e-mail (SMTP) / webhook + плашка «Состояние» в админ-панели.
* **Готово когда:** через неделю работы диск не растёт выше расчётного бюджета, ретенция подтверждена, в Grafana есть дашборды «Обзор», «Realtime», «Логи».

### Фаза 7 — Кроссплатформенность, UX и качество · ≈ 8–12 ч + ожидание людей · ~4–5 дней
* Playwright-матрица: Chromium, Firefox, **WebKit**, эмуляция iPhone/iPad; визуальные снимки ключевых экранов.
* Ручной чек-лист на реальных iPhone/iPad/Mac Safari (печать, буфер, загрузка файлов, фон/возврат вкладки).
* Адаптивность (<700 px — табы), touch-цели ≥ 44 px, safe-area, a11y-проход.
* **UX-полировка и юзабилити-тест** (3–5 операторов + админ, без инструкции; цель: первый билет < 60 с, SUS ≥ 80), профилирование плавности (нет кадров > 50 мс), проверка `prefers-reduced-motion`.
* Бюджет производительности: стартовый JS ≤ 250 КБ gzip, LCP < 2.5 с на 4G; профилирование таблицы.
* Security-ревью (`security-guidance`, `govulncheck`, `npm audit`), CSP, rate-limits.
* **Языки и темы:** перевод на узбекский проверен носителем, глифы узбекской латиницы в шрифтах билета, вёрстка на длинных строках, контраст светлой темы (WCAG AA), снимки Playwright: 2 темы × 2 языка.
* **Готово когда:** чек-листы пройдены, критичных/высоких находок нет.

### Фаза 8 — Выкатка · ≈ 3–4 ч + доступ к серверу · ~1–2 дня
* Prod-compose, Caddy (TLS, HTTP/2/3, brotli), секреты, первичный админ, smoke-тесты.
* Репетиция восстановления из бэкапа, ранбук, передача заказчику.

**Итого: ≈ 55–80 часов активной работы, ≈ 17 рабочих дней по календарю при быстрых согласованиях; с запасом на правки и ожидание — 4–5 недель** (для сравнения: у разработчика-человека те же 37–41 рабочий день, ≈ 8–9 недель).

| Сценарий | Срок | Условия |
|---|---|---|
| Оптимистичный | ≈ 3 недели | Согласования в тот же день, нет сюрпризов на iOS/Safari, сервер и аккаунты готовы заранее |
| **Ожидаемый** | **≈ 4–5 недель** | Согласования в течение суток, умеренное число правок после показов |
| Пессимистичный | ≈ 7–8 недель | Сложные баги Safari/WebSocket, переделка светлой темы, задержки перевода/сервера/тестеров |

Где ускорение от того, что код пишет ИИ, **не** работает: реальные устройства (iPhone/iPad/Mac), проверка узбекского носителем, согласование дизайна светлой темы, юзабилити-тест с живыми операторами,
доступ к серверу/домену/SMTP/хранилищу бэкапов, приёмка заказчиком. Эти шаги вынесены в «Допущения и что нужно от вас» ниже.

Объём кода оценочно 25–30 тыс. строк с тестами — построчно вы его не прочитаете, поэтому качество подтверждается тестами (unit/интеграционные/e2e), автоматическим ревью (`/code-review`, проверка безопасности) и вашей приёмкой на майлстоунах.
**Как ускориться:** если разрешите запускать параллельных агентов (бэкенд и фронтенд одновременно), календарь сократится примерно на 20–25 % за счёт большего расхода токенов.

## 6. Definition of Done (для каждой задачи)
* Архитектура: код соблюдает правило зависимостей (CI: `depguard` + архитектурный тест); бизнес-логика — только в `domain`/`service`; цепочка `handler → service → repository` без обходов (handler не зовёт repository); `service`/`repository` не логируют.
* Тесты по слоям: `domain` — unit; `service` — на фейках интерфейсов (основная масса, без БД); `repository` — интеграционные (Postgres/Redis в testcontainers); `handler` — `httptest` и контрактные тесты; для UI — компонентные и e2e на критичных путях.
* `go vet`, `golangci-lint`, `go test -race`, `tsc --noEmit`, Biome — без ошибок.
* Миграция обратима (`Down`), без блокирующих DDL на больших таблицах.
